# Job-Pipe v0.3.1 implementation report

## Implementation

Implemented structured persistent applicant knowledge, local verification,
readiness and batch clarification, deterministic routine answers, and explicit
MCP draft preparation. Release metadata is 0.3.1. Changes remain unstaged on
`feat/v0.3.1-applicant-readiness`; no Git history operations were performed.

Files added:

- `jobpipe/applicant_models.py`: strict fact vocabulary and typed interface models.
- `jobpipe/applicant_schema.py`: additive SQLite schema.
- `jobpipe/applicant_profile.py`: current facts, revisions, proposals, import,
  confirmations, corrections, consistency checks and compatibility projections.
- `jobpipe/applicant_cli.py`: trusted local applicant review commands.
- `jobpipe/readiness.py`: readiness, questions, package freshness and answers.
- `tests/test_applicant_profile.py`, `tests/test_applicant_readiness.py`, and
  `tests/test_applicant_mcp.py`: synthetic regression and protocol acceptance tests.
- `docs/APPLICANT_PROFILE.md` and this report.

Files modified:

- `jobpipe/db.py`, `jobpipe/eligibility.py`, `jobpipe/services.py`: additive
  initialization, canonical applicant snapshots and shared orchestration.
- `jobpipe/agent_models.py`, `jobpipe/mcp_server.py`: typed tools, permissions,
  structured errors, privacy-safe applicant diagnostics and preparation modes.
- `jobpipe/application_package.py`, `jobpipe/job_requirements.py`,
  `jobpipe/tailor.py`, `jobpipe/cli.py`: verified projections, factual rendering,
  draft labels, local review registration and protection of existing packet files.
- `jobpipe/__init__.py`, `pyproject.toml`: version metadata.
- `tests/test_mcp.py`, `tests/test_agent_discovery.py`,
  `tests/test_discovery_integrity.py`: updated tool discovery and explicit
  applicant-read permissions while retaining prior workflow assertions.
- `tests/test_audit_learning.py`: isolate cwd-bound artifacts/profile reads as
  well as its database.
- `docs/AGENT_INTERFACE.md`: v0.3.1 interface and migration documentation.

Four additive tables are created through the existing explicit initializer:
`applicant_profiles`, `applicant_facts`, `applicant_fact_revisions`, and
`application_package_provenance`. Current facts are unique per applicant/key.
Transactions and expected revisions prevent partial verification and stale
overwrites. Historical values and rejected alternatives remain inspectable.

Verification statuses distinguish verified, self-reported, imported-unverified,
inferred and unknown values. Provenance records source, reference, evidence,
timestamps, review state and predecessor. Agent proposals use inferred status
and agent origin. Applicant confirmation creates a new attested revision.

CLI commands: `applicant show`, `import`, `review`, `edit`, `history`,
`readiness`, and `questions`. Import previews the existing candidate YAML and
Markdown format; explicit local acceptance activates SQLite. Original files are
preserved. Explicitly verified legacy facts retain their evidence; other imported
claims require review. Packaged examples are skipped.

New MCP tools: `get_applicant_profile`, `get_applicant_readiness`,
`get_application_readiness`, `get_readiness_questions`,
`propose_applicant_facts`, and `get_application_answer`.

Existing eligibility remains authoritative through a canonical-profile adapter;
existing search goals and canonical fit scoring are unchanged. Both existing
rendering paths receive verified projections after cutover. No duplicate
eligibility engine or résumé-generation pipeline was introduced.

## Permissions and privacy

Applicant reads require `--enable-applicant-profile-read`. Proposals additionally
require `--enable-applicant-fact-proposals`. Existing detailed eligibility tools,
source trials and preparation also require applicant-read authority because their
outputs depend on private evidence. Ordinary job searches remain available.

`--enable-local-writes` grants only saving/preparation; it cannot confirm or
modify current verified facts. The trusted management boundary is direct local
CLI review with exact values displayed and revision checks. No MCP confirmation
tool or `confirmed=true` argument is accepted.

SQLite is local and unencrypted. Default profile sections omit identity/contact,
and section filtering limits returned values/provenance. No applicant HTTP
endpoints or external profile services were added. Fact keys do not support
credentials; evidence must also be kept free of secrets. Imported text and
references remain inert data. Private applicant-operation errors avoid logging
values. Tests and diagnostics contain synthetic applicant information only.

Production applicant files, learned weights and existing packages were not
migrated or rewritten. A temporary synthetic bundle created by an initially
insufficiently isolated regression test was removed; that fixture now isolates
its working directory too.

## Readiness

Eligibility remains eligible/ineligible/needs-review independently of fit.
Missing facts remain unknown. Country authorizations remain independent;
projects are not employment; completion is not current enrollment; a language
name is not fluency. Conflicts withhold relevant conclusions. Numeric experience
and explicitly attested ranges remain distinct; ranges do not become exact ATS
answers.

Question batches default to five, permit up to 20, and evaluate at most 100
selected jobs. Questions deduplicate by fact/context, retain actual potentially
affected job IDs/counts, and rank by count, blocking relevance, existing goal
modifiers, evidence strength and reuse. Employer uncertainties remain separate.
Resolved facts eliminate questions across later sessions; concurrent profile
changes invalidate mixed readiness snapshots.

Default MCP preparation retains the eligible-only gate. Explicit
`draft_preparation` permits needs-review jobs with visible draft labels and
blocked readiness. Ineligible MCP preparation is denied. Manual drafting remains
available without changing its existing feedback/application-status semantics.

Package metadata tracks profile revision, job/search context and file hashes.
Existing files are preserved byte-for-byte. Legacy, stale, edited, incomplete and
draft packages cannot silently become ready. The positive state is
`ready_for_human_review`, not submitted or externally authorized.

## Architectural assessment

1. **Can any authorized MCP-compatible agent retrieve the profile?** Yes: typed
   vendor-neutral stdio tools require explicit applicant-read capability.
2. **Can one agent propose facts another uses after verification?** Yes: the
   real independent-session acceptance demonstrates persisted proposals,
   separate local confirmation, and subsequent retrieval/eligibility.
3. **Are confirmed facts distinct from agent proposals?** Yes: verification,
   source origin, review state, timestamps and revision history distinguish them;
   MCP cannot attest.
4. **Can missing eligibility information be consolidated across jobs?** Yes:
   stable fact/context questions carry deduplicated affected-job counts.
5. **Do verified updates reevaluate eligibility?** Yes: checks recompute on
   demand from the current profile, with revision/configuration identity; package
   freshness also detects changes.
6. **Can agents draft without falsely declaring readiness?** Yes: explicit
   needs-review drafts are labeled and blocked, independently of file existence
   or canonical application status.
7. **Are already available answers reused?** Yes: verified supported answers
   remove resolved questions and remain available across agents/sessions.
8. **What remains before an external executor?** Employer-specific form mapping
   and completeness checks, document approval/version handling, explicit
   submission authorization, sensitive-question decisions, duplicate protection,
   receipts, and recoverable execution failures.

## Limitations

- There is no external application executor, browser form automation, CAPTCHA
  handling, submission, or employer communication.
- Eligibility covers the existing supported posting constraints, not every
  possible employer rule, current vacancy, or application form.
- Imports support the existing YAML/Markdown formats, not general document OCR
  or PDF/DOCX ingestion. Ambiguous source dates remain evidence.
- Experience ranges and unsupported questions require review rather than guessed
  precision or an LLM-generated answer.
- Local CLI confirmation assumes a trusted single-user OS environment; it is
  not identity proof against arbitrary local shell/database access.
- SQLite/materials are not encrypted. Authorized clients and local backups must
  be trusted. Source references are not independently authenticated evidence.
- Existing/stale/edited bundles need local review or explicit replacement;
  automated merging and silent promotion are deliberately unavailable.
- Filesystem publication and database bookkeeping are not one atomic resource;
  a complete orphan bundle is preserved and cannot acquire readiness merely
  because its files exist. No background reconciliation architecture was added.
